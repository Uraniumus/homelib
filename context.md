# Домашняя библиотека — контекст проекта

Документ для переноса контекста в новую сессию (Claude Code / VS Code).
Схема БД лежит отдельно в `library_schema.sql` — это источник истины по модели данных.

---

## Что за продукт

Multi-user веб-приложение для учёта личной библиотеки:

- каталог книг с точной моделью изданий (важны советские издания без ISBN);
- коллекции экземпляров с полками, состоянием, фото;
- выдача книг «в аренду» — как зарегистрированным пользователям, так и
  незарегистрированным контактам (мама, дядя Коля);
- читательский дневник: отметки «хочу / читаю / прочитано / брошено» и отзывы
  с видимостью public / friends / private, в том числе про книги вне своей коллекции;
- пользовательские теги и шарибельные подборки; в перспективе — лента как в соцсети.

Целевая аудитория на старте — до 1000 пользователей, преимущественно с телефона.

## Модель данных: принятые решения и почему

Схема — в `library_schema_v3.sql` (PostgreSQL). Ключевые решения, которые нельзя
«упростить» без потери смысла:

**Три слоя вместо одной сущности «книга».**
`works` (произведение — текст как таковой) → `editions` (издание конкретного
издателя) → `copies` (физический экземпляр на полке). Причина: у одного
произведения бывает несколько изданий, у одного издания — несколько экземпляров,
и пользователь целенаправленно держит и советское издание, и переиздание.

**ISBN — не первичный ключ и не unique.** Это идентификатор издания, а не
произведения; у советских изданий его нет вовсе, у переизданий он совпадает,
а на обложках встречаются ошибки. Все идентификаторы вынесены в
`edition_identifiers` (тип-значение) со справочником `identifier_types`
(isbn13, isbn10, ББК, УДК, номер заказа...). Уникальность — только внутри издания.

**Связь `edition_works` — many-to-many, и это покрывает оба случая:**
сборник (одно издание → много произведений, поле `position` — порядок в оглавлении)
и многотомник (одно произведение → много изданий, поле `part` — какая часть текста).

**Авторы — на произведении, переводчики — на издании.** Отсюда две таблицы связей
(`work_contributors`, `edition_contributors`) поверх общей таблицы `persons`.
Это частая ошибка в подобных схемах, не сливать.

**Каталог общий, личное — приватное.** `works`, `editions`, `persons`, `publishers`
общие для всех пользователей (иначе одна книга заводится сто раз), на них стоит
`created_by`. Личное: `collections`, `copies`, `loans`, `book_marks`, `reviews`,
`lists`, `user_tags`, `contacts`.

**Аренда сама себе лог.** Не флаг на экземпляре, а строки в `loans`:
`due_at IS NULL` = бессрочно, `returned_at IS NULL` = ещё на руках.
Частичный уникальный индекс запрещает две активные аренды одного экземпляра.
Заёмщик — ровно один из двух: `borrower_user_id` или `borrower_contact_id` (CHECK).

**Отзывы и отметки: `work_id NOT NULL`, `edition_id` опционально.**
Отзыв концептуально про произведение, но если речь про конкретный перевод
или качество печати — уточняется изданием. Отметки не имеют «текущего статуса»:
перечитывание = ещё одна строка, актуальный статус = последняя по `created_at`.

**Теги vs локации vs подборки — три разные вещи, намеренно не объединены:**
- `locations` — справочник полок внутри коллекции, у экземпляра ровно одна (FK);
- `user_tags` + `work_user_tags` / `copy_user_tags` — теги пользователя;
  жанры вешаются на произведение, «утилизировать» — на экземпляр;
- `lists` + `list_items` — шарибельные подборки; элемент это **произведение или
  издание, но не экземпляр** (CHECK на ровно одно из двух), потому что подборку
  видят другие люди, а чужой `copy_id` для них бессмыслен.

**Почему теги не в jsonb:** по ним фильтруют, группируют и их переименовывают —
это три операции, на которых json-массив проигрывает таблице (переименование =
перезапись всех строк, счётчики = распаковка jsonb по всей таблице, автодополнение
невозможно, опечатки плодят дубли). jsonb в этой схеме используется только там,
где данные разнородные и по ним не джойнят.

**Таймстемпы:** `created_at` / `updated_at timestamptz` на всех таблицах,
`updated_at` обновляется общим триггером `touch_updated_at()`.
Дата отзыва / отметки — это и есть `created_at`, отдельных полей нет.

**Фото:** файлы в объектном хранилище, в БД только ключ (`copy_photos.storage_key`,
uuid генерирует приложение) — хранилище не должно знать про доменные id.
`editions.cover_path` — каноническая обложка (общая для всех),
`copy_photos` — фото конкретного экземпляра (корешок, автограф), несколько штук.

**`copies.is_hidden`** — скрытый экземпляр виден только владельцу;
фильтруется до проверки `visibility` коллекции. Скрытую книгу выдавать в аренду можно.

### Известные незакрытые места в схеме

- FK `copies.location_id` не гарантирует, что полка принадлежит той же коллекции,
  что и экземпляр. Сейчас на совести приложения; железный вариант (составной FK
  через `UNIQUE (collection_id, id)` на `locations`) описан комментарием в файле.
- Лента соцсети: схема к ней готова (везде есть `visibility` + `friendships`),
  на MVP это просто запрос по `reviews` / `book_marks`. Отдельная append-only
  таблица `activities` заводится позже, когда упрёшься в агрегацию событий и лайки.
- `collections` трактуются как физические места (дом, дача), экземпляр лежит
  ровно в одной. Тематические подборки — это `lists`, не коллекции.

## Стек и решения по исполнению

- **Nuxt как fullstack** (серверные роуты Nitro в `server/api/`) — одна кодовая база,
  один деплой. Главная причина именно Nuxt, а не SPA на Vue: подборки, отзывы и
  профили шарятся ссылками, значит нужен SSR ради превью в мессенджерах и индексации.
- **Drizzle ORM** — схема как код, запросы близки к SQL, миграции из диффа схемы.
- **PostgreSQL**, **объектное хранилище S3-совместимое** для фото.
- **Загрузка фото через presigned PUT** — браузер грузит напрямую в хранилище,
  минуя сервер приложения.
- **Авторизация** — сессионная (`nuxt-auth-utils`).
- **Деплой** — docker compose (Nuxt + Postgres + Caddy для https) на одном VPS.
- **Бэкапы** — свой `pg_dump` по крону в объектное хранилище (класс Cold),
  а не платный бэкап провайдера: он дороже сервера и не переживает смерть провайдера.

### Мобильная стратегия

PWA как основа (иконка на экране, полноэкранный режим, офлайн-кэш), потому что
продукт распространяется ссылками и нативное приложение эту механику ломает.
Камера и сканер штрихкодов ISBN работают в вебе. Позже:
TWA для Google Play (собирается за вечер через Bubblewrap/PWABuilder),
iOS-обёртка на Capacitor — последней, сразу с нативными пушами и камерой,
иначе есть риск отклонения по правилу о минимальной функциональности.
Подписку внутри iOS-приложения не продавать (комиссия Apple) — только на сайте.

## Экономика (для контекста решений, не для кода)

- Инфраструктура на 1000 пользователей: сервер ~600 ₽/мес + хранилище ~100 ₽/мес
  + домен ≈ 750–800 ₽/мес. Точка безубыточности при подписке ~149 ₽/мес — 5 подписчиков.
- «Вечный» сервер за 30 000 ₽ разово отклонён: окупаемость ~4 года, конфигурация
  заморожена, риск провайдера. Решено брать обычный VPS.
- Бесплатный тариф: до 100 книг. Сама БД почти ничего не стоит (100 книг ≈ 0.5 МБ),
  реальный расход — фото, поэтому лимит вешать и на фото тоже
  (например, 3 фото на экземпляр на бесплатном тарифе).
- **Обязательные предохранители до запуска:** лимит размера загружаемого файла
  (сжатие до ~300 КБ + жёсткий отказ на >10 МБ), счётчик фото на экземпляр,
  алерт на биллинг.

## Как поделена работа

Пользователь пишет проект сама, цель — прокачаться как fullstack-js разработчик.
Поэтому:

- **Ассистент делает:** порт схемы в Drizzle, docker-compose и конфиги,
  сид-скрипт с фикстурами, каркас тестов (vitest + тестовая БД + фабрики),
  README по деплою, ревью написанного кода, скучные краевые кейсы в тестах.
- **Пользователь пишет сама:** серверные роуты и Vue-компоненты, основные тесты.
  Первый роут и первый компонент делаются вместе как образец паттернов —
  дальше самостоятельно, с ревью.

Не надо писать за неё фичи целиком без просьбы. Ревью, паттерны, инфраструктура — да.
